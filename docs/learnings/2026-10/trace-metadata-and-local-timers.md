# Trace 为什么要选取元数据，并自己配对计时

调试输出常见的泄露来源是直接格式化整个回调参数：`print(call)` 会带出实参，`print(result)` 会带出工具结果，`print(error)` 会带出异常文本。观察器收到的信息多于它应该输出的信息，因此“回调参数可以访问”不意味着“字段可以写入 Trace”。

在本项目中，工具开始输出只选择 call.name 和 call.id，成功只选择标识与本地耗时，错误只选择 ToolHookError.error_type。模型上下文只选消息数量和模型标识；不格式化 Message、ModelResponse、usage 或工具结果。测试把不同秘密标记放进实参、结果、用户消息、异常和模型文本，检查这些标记都不在 stderr。断言执行结果仍正确，避免把没有执行任务误判为隐私通过。

即使某字段名看起来属于元数据，也要确认它的值来源。finish_reason 来自响应，非法值可能是任意文本；输出时只接受已知类别，其余归为 unknown。工具名与调用 ID 属于允许显示的标识，但仍需转义控制字符，防止它们通过换行或终端控制序列伪造另一条日志。

计时的另一个陷阱是依赖 Hook 上下文对象身份。内核为每次回调创建独立快照，开始与结束收到的不是同一对象。观察器需要使用语义稳定的 call.id 来配对自己保存的计时起点：

```python
starts[call.id] = monotonic()
duration_ms = max(0, (monotonic() - starts.pop(call.id)) * 1000)
```

使用单调时钟能避免墙上时间校准导致计时倒退。测试可替换时钟模拟不同起点和倒退，验证多工具按 ID 配对与非负输出。准备失败没有实际执行起点，所以不应伪造 started 或执行耗时；取消没有正常结束回调，所以在 on_finally 中尽力显示未结束工具，并在 finally 中清空字典，即使输出流已关闭也要释放观察状态。

自检时可以问：这条输出包含了完整对象吗？结束回调能否通过 ID 找到正确起点？准备失败与实际执行失败能否区分？取消或 stderr 写入失败后，字典是否仍有旧起点？这些问题比“日志看起来详细”更有助于验证一个轻量观察器。
