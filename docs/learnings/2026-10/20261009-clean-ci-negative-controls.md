# 负对照不能依赖开发机的隐含资源

## 为什么本机绿灯还会在 CI 失败

“配置读取必须被哨兵阻断”的负对照，如果指向开发机已有但 Git 忽略的 `.env`，就依赖了一个没有声明的测试输入。干净 checkout 中没有该文件，配置库会先检查存在性，根本不进入 open；此时“没有抛出错误”不能证明哨兵失效，也不能证明生产行为改变。

测试要证明的不是“我的电脑有某个文件”，而是“如果有人错误启用 dotenv 源，读取必然被拦住”。

## 怎样保持验证强度

1. 正向用例禁用 dotenv 源，禁止个人文件读取，验证 API 可以正常启动与查询。
2. 在临时目录写入无敏感内容的合成 dotenv，明确保证负对照文件存在。
3. 哨兵同时拦截个人与合成路径；负对照仅启用合成源，断言在读取内容前抛错。
4. 保留配置恢复与环境隔离，避免这个负对照污染后续用例。

不要为了修 CI 去掉负对照、创建仓库 `.env`、复制个人配置或跳过 Linux/macOS。**输入必须可控，预期失败也必须可复现。**

## 自检

- 删除全部未提交文件后，这个测试还会触发相同的路径吗？
- 负对照失败说明安全约束失效，还是只说明测试输入不存在？
- 测试是否有可能在哨兵安装前读到个人数据？
