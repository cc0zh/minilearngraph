# 为什么要把会话历史和模型—工具循环分开

一轮用户输入可能需要模型请求多次：模型提出工具调用，程序执行工具，再把结果交给模型生成答案。这里有两个不同的生命周期：会话跨越多轮输入，执行循环只属于当前这一轮。

AgentLoop 保存会话历史并取得当前领域快照；AgentRunner 接收已组装的消息，用局部变量执行模型—工具循环并返回新增消息。这样同一个 Runner 可以服务不同的 Loop，而不会把一个会话的数据带到另一个会话。

## 工具结果为何必须配对

工具调用不是一条普通聊天文本。模型先发出 assistant 消息，列出调用 ID 和参数；程序再为每个调用追加 tool 消息，用同一个 ID 标明结果来源。同轮多个工具先全部得到结果，再请求模型。

```text
user: 查询时间并计算
assistant: tool_calls=[time_1, calc_1]
tool: tool_call_id=time_1，时间结果
tool: tool_call_id=calc_1，计算结果
assistant: 最终回答
```

把工具结果写成 user 消息会丢失来源；只保存 tool 消息会丢失调用依据。验收应检查下一次模型请求中的完整链，而不仅检查最终文字。

## 历史何时提交

Runner 的工作消息用于继续当前执行，Loop 的历史用于下一次用户输入。只有 completed 才把当前 user 消息和新增 assistant/tool 消息加入历史。模型请求失败或响应非法时，工作链可以返回给调用者观察，但不提交给下一轮。这是内存会话的一次整体更新，不需要引入运行状态机或事件存储。

上下文快照也要随着当轮 user 消息提交。下一轮取得新快照，旧快照保留当时的节点标识，模型才能理解“刚才那个概念”。即使本轮上下文暂时不存在，历史中的快照仍需声明为参考数据，不能移除其解释规则。

## 最后一次模型请求为什么不执行工具

工具结果需要下一次模型请求才能解释。若请求预算已经用完还执行工具，结果便没有机会回传，甚至可能执行不必要的写操作。因此看到最后一次请求仍要求工具时，应直接返回 step_limit。

调用预算计算的是模型请求次数，不是工具个数。同轮两个工具只消耗当前模型请求，下一次请求才能消费它们的结果。

## 自检

- 同一 Runner 连续运行两次，会不会读取上一次的工作消息？正确实现只有局部执行状态。
- 工具链执行一半遇到程序缺陷，下一轮会不会看见未闭合的链？Loop 只提交 completed。
- 模型桩回答看起来正确，能否证明兼容真实模型？不能；桩证明内核按契约运行，真实模型的协议支持与实际输出需要单独验证。
